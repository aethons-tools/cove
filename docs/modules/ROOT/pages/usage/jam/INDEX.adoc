= `jam` — operating the central service
:summary: Section index for operating `jam` — the durable central service that brokers a studio's credentials/egress, holds the actor roster (RBAC), and serves the kit registry.
:read_when: You are running or administering a Jam service — standing it up, signing an operator in, deciding who can reach what, or registering kits — and need the map of its operator docs.
:owns: the map of the jam operator/usage docs and how they relate
:prereqs: ../../OVERVIEW.adoc for the studio image and its security model
:tier: section
:updated: 2026-11-13

`jam` is a *durable, always-on host service* that a fleet of hardened
studios points at. It does three things for the studios it serves:

* *Brokers credentials + egress* — a studio reaches Anthropic and git through
Jam with only a scoped _identity token_; Jam holds the real credentials
and injects them. The high-value secrets live in Jam, never in the studio.
* *Holds the roster (RBAC)* — a top-level *Actor* (one identity + token) is
granted **Role**s within **Project**s; a Role owns the security scope the broker
enforces.
* *Serves the kit registry* — named, versioned kit definitions a Role can bind.

`jam` ships as one binary (minting is `jam mint`), released alongside
xref:usage/jam-colima.adoc[`jam-colima`] for remote manager hosts: install
them with the one-command installer and keep them current with `jam update` (see
xref:OVERVIEW.adoc#installing-the-binaries[installing the binaries]).

This is the _how to run and administer it_ layer.
For _why_ it's built this way (threat model, the broker's boundary relocation, the
five pillars), see the design history:
https://github.com/aethons-tools/cove/blob/main/docs/superpowers/specs/2026-09-10-harbor-design.md[`../../superpowers/specs/2026-09-10-harbor-design.md`].

== The shape of a working Jam

. *Run it* — write a serve config and start `jam serve` (xref:usage/jam/serve.adoc[serve.adoc]).
. *Gate the admin API* (beyond loopback) and sign in (xref:usage/jam/operators.adoc[operators.adoc]).
. *Point it at its config repo* (xref:usage/jam/config-git-sources.adoc[config-git-sources]): config
changes only by a commit to it, by hand or on a branch (xref:usage/jam/config-branches.adoc[config-branches]).
. *Commit the project* (xref:usage/jam/projects.adoc[projects.adoc]), *destinations, roles* and *kits*
(xref:usage/jam/kits.adoc[kits]), then *enroll* studios or grant roles (xref:usage/jam/roster.adoc[roster.adoc]).
. *Raise managed studios* against a role and track them through the runtime
registry (xref:usage/jam/coves.adoc[coves]).

Every admin verb (`destination`, `model-spec`, `project`, `role`, `grant`, `ungrant`, `actors`, `enroll`,
`revoke`, `kit`, `studio`, `session`, `standing`, `config`) is a thin client of the running Jam's admin API: it takes
`+--app+`/`+--admin-url+` to pick the target and `+--token+` (or a cached login) to
authenticate. That client story lives in xref:usage/jam/operators.adoc[operators.adoc]; the
per-verb detail lives in the docs above.
