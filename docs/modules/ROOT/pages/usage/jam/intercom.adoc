= The intercom MCP
:summary: The intercom MCP — Jam-brokered read/commit/send/list_targets/escalate tools a managed studio's agent uses to converse in channels (its ticket's, a chat, a room) on the channel log. Tokens stay in Jam; the endpoint is broker-authorized; the tools reach claude via a `jam-studio-agent mcp` stdio server.
:read_when: You want a raised studio's agent to be able to read and post comments on the ticket it's working (ask a question, leave a status), or you're wiring/operating Jam `/squawks` endpoint and its cove-side MCP delivery, the relays, or running the intercom on a Jam with no Requisitioner.
:owns: the operator-facing intercom-MCP story — the `/squawks` broker endpoint and its wire shapes, the `mission` and `focus` tools and their `PUT /mission` and `PUT /focus` endpoints, content types, the channel log and its cutover from the legacy log, channel membership (call-in, join, leave), the inbox as a queue, the relays, the `jam-studio-agent mcp` stdio delivery, and how it's enabled. Does NOT own the target space or access-graph rules — see comms-addressing.md. Does NOT own escalation-category semantics for the `escalate` tool — see escalation.md. Does NOT own wake-on — see wake-on.adoc.
:prereqs: coves.adoc for the managed studio a squawk is scoped to; personal-sessions.adoc for a ticketless studio that talks to the person who started it; requisitioner.adoc for the tracker/Linear client this reuses; roster.adoc for the identity a squawk is attributed to; comms-addressing.adoc for addressing a target other than the studio's own ticket
:tier: leaf
:updated: 2026-11-13

NOTE: The goal replaces session and ticket channels with DMs, rooms, and units of work. Where this page disagrees with xref:usage/jam/conversations.adoc[conversations], that page wins.

A managed studio's agent gets *Jam-brokered* tools — `read`, `send`,
`+list_targets+`, and `escalate` — over Jam's *channel log*: every squawk is in
one channel (a ticket's conversation, a session's own channel, a chat with people, a room) and reaches
that channel's members. Jam holds the tracker token, does the platform I/O, and attributes the sender; the studio never holds a channel token, exactly like the Anthropic and git connectors. This is the imperative foundation of the comms hub (slice A of A→B→C).

[#what-the-tools-do]
== What the tools do

* *``+send(text, to?, content_type?)+``* — posts the squawk to a channel of the channel log and returns its id and channel (``+200 {"id", "channel": {id, kind, label}}+``; a studio on an older image just sees success); the relays render it onto Linear/Discord shortly after (see <<enabling-it,Enabling it>>). With no `to`, it goes to the studio's *home channel*, the channel it is always in: its own *session channel*, whatever started it (a ticket session is also a member of its ticket's conversation, so the issue's comments reach and wake it, and posts there with ``+to: ticket:<its key>+``; for a xref:usage/jam/personal-sessions.adoc[personal session] the person who started it is in it; people can join a xref:usage/jam/standing-sessions.adoc#messaging[standing session]'s). With a `to` (`+user:+`, `+chat:+`, `+channel:+`, `+ticket:+`, `+session:+`) it goes to that channel instead — see xref:usage/jam/comms-addressing.adoc[comms-addressing] for the target space, authorization, and delivery/reply rules (single source; not duplicated here). The author is Jam's brokered identity (the agent can't spoof it). The body is markdown unless `+content_type+` opts out; see <<content-type-markdown-or-plain-text,Content type>>.
* *``read(anchor?, id?, dir?, limit?)``* — reads the studio's inbox *as a queue*: the squawks delivered to it (others' posts in its channels), by default the next unprocessed ones after its durable commit cursor, oldest-first. Seek with `anchor` (`cursor` default / `start` / `end` / `id`) × `dir` (`forward` default / `backward`) × `limit` (default 50); the response also carries `+committed_cursor+` / `+page_first+` / `+page_last+`. Each entry has `channel` (``+{id, kind, label}+``; absent on a squawk from before the cutover) and `from` (`+{id, kind: session|user|account, label}+`), and keeps `author` (the sender's label) for older clients. *Reading never advances the cursor.* Self-scoped: `read` takes no target. See <<the-inbox-as-a-durable-queue,The inbox as a durable queue>> below.
* *``+commit(up_to)+``* — confirms the studio has processed its inbox up to a squawk id, advancing its durable commit cursor (monotonic, forward-only) so those squawks aren't handed to it again. Separate from `read` — reads don't commit. Self-scoped (the cursor is the caller's own; identity comes from the token, never the body).
* *``+list_targets()+``* — lists the people, rooms and sessions this studio is currently authorized to ``+send(to=…)+``; see xref:usage/jam/comms-addressing.adoc#discovering-targets-get-squawkstargets-list_targets[comms-addressing].
* *``mission(text)``* — sets the session's *mission*: one line naming its end goal or standing order (what it was started for; it changes rarely), shown beside its name in the xref:usage/jam/intercom-ui.adoc[inbox], in the xref:usage/jam/session-view.adoc#header[session header] and on its xref:usage/jam/intercom-ui.adoc[status card] (`PUT /mission` `+{"text"}+` → ``204``; `400` malformed JSON, `401` unknown or missing identity, `403` no instance, `413` body over 2 KiB, `405` other methods). Jam drops control and Unicode format characters (e.g. NUL, bidi overrides), trims the text, collapses every whitespace run (newlines too) to one space, and cuts anything over 120 runes to 119 plus ``+…+``; empty text clears it. Self-scoped: it sets the caller's own session, there is no target. A ticket session starts with its xref:usage/jam/requisitioner.adoc#the-flow-per-poll[ticket's title]; a Clear resets it (xref:usage/jam/session-view.adoc#session-controls[session-view.adoc]); a restarted standing session is told to set it again. It shows on the next rail or header refresh (up to 30s), not instantly. The session context tells agents to set it (xref:usage/jam/session-context.adoc[session-context.adoc]).
* *``focus(text)``* — sets the session's *focus*: one line saying what it is on right now, changing with each step; carried on its xref:usage/jam/intercom-ui.adoc[status card] (`card.focus`). It works exactly like `mission` — `PUT /focus` `+{"text"}+`, the same responses, normalisation, 2 KiB cap and self-scoping — except that a session starts with none. A change pushes a live card update (the `presence` signal, xref:usage/jam/intercom-ui.adoc[intercom-ui]); a Clear resets it too, and a restarted standing session is told to set it again; the session context tells agents to set it whenever their focus changes.
* *``+call_in(who, channel?)+``* and *``leave(channel)``* — membership (`POST /squawks/call-in` → `+200 {channel, member}+`, `POST /squawks/leave` → `204`); see <<channel-membership,Channel membership>>.
* *``report(state, summary, pr?)``*, *``end(reason)``*, *``+idle_timeout(duration, scope)+``* and *``+alarm_set+`` / `+alarm_clear+` / ``+alarm_list+``* — report a ticket's state, end the session at turn end, tune how long it may sit idle after one, or set named alarms that wake it; see xref:usage/jam/turn-end.adoc[turn-end.adoc].
* *``expose(port, name)``*, *``unexpose(name)``* and *``exposures()``* — publish a port the session serves as a named xref:usage/jam/previews.adoc[studio preview] and get its URL to post in the channel (`PUT`/`+DELETE /exposures/{name}+`, `GET /exposures`); answer 409 until the Jam has a preview domain configured. Listed in the session context only when previews are enabled; see xref:usage/jam/session-context.adoc[session-context.adoc].
* *``+send(…, attach?)+``* and *``fetch(ref, path?)``* — attach files from the studio to a message, and download one into it; see xref:usage/jam/attachments.adoc[attachments].
* *``+board_create+``*, *``boards``*, *``+board_read+``*, *``+board_apply+``*, *``+board_snapshot+``* — sketch with people on a conversation's whiteboard; see xref:usage/jam/whiteboards.adoc[whiteboards.adoc].
* *``ask(question, options, to?, of?)``*, *``amend``*, *``withdraw``* and *``asks``* — ask people a question with answers to pick from; the answer arrives through `read` as an entry carrying its ask part (`parts`). See xref:usage/jam/asks.adoc[asks].
* *``escalate(category)``* — asks for a person: declares the block's category (picking the escalation tier chain) and, until the session is next woken, opens an escalation once it waits — its tiers are called into the session's channel; see xref:usage/jam/escalation.adoc#when-it-opens-waiting-and-asking-for-a-person[escalation].

The agent blends these with its work inside a turn — e.g. leave a status, read the next unprocessed replies, handle them, `commit` up to the last one it handled. See xref:usage/jam/wake-on.adoc[Waiting for a reply] for suspending until a reply arrives.

[#content-type-markdown-or-plain-text]
== Content type: markdown or plain text

Every squawk carries a `+content_type+` (a MIME type) saying how its body is meant
to be read:

* *``text/markdown``*: the *default*. A send that omits `+content_type+`, a
Linear comment, and a Discord message are all markdown. Squawks logged before
the field existed read back as markdown too.
* *``text/plain``*: the *opt-out*, for text that would render badly as
markdown (logs, ASCII art, stray `+*+` and `+_+`). Every surface shows it
literally, never interpreted as markdown.

Each side can opt out:

* an agent passes `+content_type: "text/plain"+` to `send` (`POST /squawks` takes
the same optional field);
* a human ticks *Plain text* in the xref:usage/jam/intercom-composer.adoc[`/app/user` composer]
(`POST /app/user/send` takes the same field).

Anything else is a `400`, and nothing is appended. `read` (`GET /squawks`)
returns each squawk's `+content_type+`, so an agent knows when a reply is meant
literally.

*Rendering:*

* The xref:usage/jam/intercom-ui.adoc[`/app/user` inbox] and the xref:usage/jam/ui-console.adoc#channel-log[admin Channel log]
render markdown as sanitized HTML: raw HTML is omitted, `+javascript:+`-style
link targets are dropped, and links open in a new tab. Plain text is shown
as-is.
* On the relays, markdown is posted byte-for-byte. Plain text is
backslash-escaped for the surface's markdown flavor, so Linear and Discord
display it literally. For Linear, newlines also become hard breaks and
leading indentation is kept, so neither collapses nor turns into a code block.

== How it's brokered and scoped

* *Endpoint:* Jam serves `/squawks` on its cove-facing `+:443+` mux. A request carries the studio's identity token (`+Authorization: Bearer+`); Jam resolves the session from it — never from the body.
* *``read`` is self-scoped by construction:* it carries no target, so it can only ever return the caller's own inbox. *``send`` is authorized:* the home channel is always allowed; a `to` is checked against the role's addressing before anything else — see xref:usage/jam/comms-addressing.adoc[comms-addressing].
* *Tokens stay in Jam:* the Linear token lives in Jam's ``SecretResolver``; the studio holds only its identity token. Nothing is logged that could leak either.

[#delivery-to-the-agent]
== Delivery to the agent

The studio's `claude` is pointed at a stdio MCP server named `messaging` in the per-run `+--mcp-config+` that jam-studio-agent's harness generates (alongside any kit xref:usage/jam/kits-mcp-servers.adoc[`mcp-servers`], which can never replace it), which launches `jam-studio-agent mcp`. That subcommand exposes `read`/`send`/`+list_targets+` and forwards them to Jam `/squawks` (and `/squawks/targets`) over TLS through the studio's squid proxy, using the identity token + Jam address already in the studio's environment. No new binary, no new secret in the studio.

[#channel-membership]
== Channel membership

Who hears a channel is its members. A member *calls someone in* (`+call_in+`, or *Call in…* in xref:usage/jam/intercom-ui.adoc[`/app/user`]): `who` is `+user:<name|id>+` or `+session:<label|id>+` of the channel's project, and a session inviter's addressing must allow it, as for a send (`403` before `404`); a person may call in only a session they could message themselves (never someone else's personal session). The invitee joins from now on and hears the inviter's "called in" notice, which reaches people's inboxes but is never posted onto a ticket's issue or a room's surface. A *chat* never takes new members (`409`), a *room* takes people but not sessions, and calling in a member does nothing. People also *join* a channel they can see (a ticket, a room, a standing session's channel — never a personal session's, which is invite-only) by posting or with *Join*. Anyone *leaves* (`leave`, *Leave*) except a session from its own channel or ticket, and nobody leaves a chat; what was delivered stays.

[#enabling-it]
== Enabling it

`/squawks` (and `/escalate`) are always mounted: the intercom is always on, backed by the Postgres channel log (`store-postgres` is required — xref:usage/jam/serve.adoc#the-serve-config[serve.adoc]), with or without a xref:usage/jam/requisitioner.adoc[Requisitioner], so a xref:usage/jam/personal-sessions.adoc[personal session] can converse on a Jam with none. The tracker relay (Linear or GitHub Issues) needs the Requisitioner's tracker; the Discord relay and wake-on do not.

*The channel log.* Each squawk is in one channel, from one participant (a session, a user, or an _account_ — an unlinked sender on Linear or Discord), and its audience — the channel's members but the author, at that moment — is recorded with it. A *ticket channel* is created when a session is set up on a ticket (or at serve startup for one already running), bound to the issue; the session joins it, and a re-dispatched ticket's new session joins the same channel (with an empty inbox). A session with no ticket gets its own *session channel* when it is set up (or at serve startup for one already running): the session is in it for good, a personal session's starter is called in once (and may leave), and it is archived when the session ends — after Jam's notice about the end, which its members still get. A *chat* is a fixed set of people and sessions; a *room* is a project's named channel (xref:usage/jam/project-members.adoc[project-members]).

*The cutover.* Upgrading to the channel log freezes the earlier log as *legacy history*, read-only: the admin view's Legacy tab and ``/app/user``'s History show it, and seqs carry on from its tail. A session already running at the upgrade still reads (and commits past) the legacy replies to it it hadn't processed, ahead of new ones. Squawks the relays hadn't yet delivered at the upgrade are not delivered. Stop every older Jam before starting this one, and don't roll back past it.

*Outbound is log→egress (asynchronous, at-least-once).* A `send` appends to the log and returns; a resident egress loop per relay then renders it onto its channel's surfaces (≈ the egress poll interval later). An append failure returns `502`. Every author's squawks are rendered — a person's `/app/user` post too — but never back onto the surface it came from.

*Relays.* When a Requisitioner is configured, the *tracker relay* (over its tracker, Linear or GitHub Issues) posts a ticket's conversation as comments on its issue (a person's prefixed `pass:c[<name>: ]`, a session's as written), renders a room bound to an issue the same way, and @-mentions a chat's people who have no Discord inbox on the ticket of a session in the chat. Inbound, it polls the tracker's comments feed (Linear's team feed; GitHub's repo issue comments) and posts each comment on an issue a channel is bound to into that channel (idempotently); a comment on any other issue is dropped, and so are Jam's own comments (by its tracker identity). On GitHub it also drops any Bot account's comment and skips pull-request comments; it starts once Jam's login is known (a failed lookup is retried; an App token, which has none, relies on dropping bots); after a rate limit it makes no calls until `Retry-After` has passed, warning once per wait; and a delivery that can never land (an issue on another repo) is skipped with one warning instead of holding the relay behind it. The *Discord relay* (when `runtime.discord` names its connection, with or without a Requisitioner) renders chats and session channels onto their people's inbox channels and rooms onto their bound channels, and routes replies back into the conversation of the post they answer — see xref:usage/jam/discord.adoc[discord]. The *push relay* (when `runtime.push` is set; egress only) sends Web Push notifications to the people a squawk is for — see xref:usage/jam/push-delivery.adoc#how-jam-sends[push-delivery.adoc]. The relays share the cursors/markers files in xref:usage/jam/serve.adoc#the-serve-config[`state-dir`], keyed by Service; a first-enabled relay's mark is seeded to the log's tail, so it never redelivers the backlog. Wake-on reads what they post.

____
*Before relying on inbound (reply) delivery, confirm the Linear `comments` feed schema against your live Linear workspace* — specifically the `$since` scalar (`DateTimeOrDuration` vs `DateTime`) and the `+issue → team → key+` filter path. If it differs, the ingress `Poll` errors and its cursor holds (no data loss, inbound stalls) while *egress is unaffected*.

An inbound author is recorded as an *account* on its connection by their
service user id only (labelled with their display name — never matched by it).
Once an operator links that account to a user (`+jam account list --connection linear+`, then `account link`), a post in a project the user is a
member of is theirs; until then it's the account's.
____

[#the-inbox-as-a-durable-queue]
== The inbox as a durable queue

A studio's inbox is a *durable, acked queue* over the log — the squawks
delivered to it, a conversation to process in order, not an email list.

____
*Ordering is by a monotonic append sequence, not by squawk id.* Every squawk
carries an internal append `seq` (continuing across the cutover);
"oldest-first", "forward", "tail", and the commit/wake cursors are all defined
by it. Squawk *ids are identifiers, not ordering keys* — ingress ids
(`+in:linear:<uuid>+`, `+in:discord:<snowflake>+`) are deterministic for idempotent
dedup and don't sort against generated ids. The wire stays in ids
(`+committed_cursor+`/`+page_first+`/`+page_last+`/`+up_to+`); Jam resolves id↔seq.
____

* *Commit cursor.* Each studio has a durable commit cursor (its last
_processed_ squawk id), *initialized at raise to the log's tail*, so a
freshly-raised studio consumes what reaches it from then on. It is *separate
from the wake-on ``WaitSeq``* (xref:usage/jam/wake-on.adoc[wake-on]).
* *Seekable reads that never commit.* `anchor` × `dir` × `limit` page anywhere
— re-read processed history, jump to the start/end, walk from an id.
* *Explicit commit.* `+commit(up_to)+` advances the cursor (monotonic,
forward-only, idempotent); a studio that restarts before committing
re-consumes (at-least-once). Under the xref:usage/jam/structured-turn-end.adoc[structured turn end]
the studio commits what a wake showed when the turn ends.
* *Nothing is pruned* — backward/`start` reads always work.

Waiting for a reply — how a waiting studio is paused and woken, and `runtime.wake`: xref:usage/jam/wake-on.adoc[wake-on].
