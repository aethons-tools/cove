= The Jam credentials file
:summary: The protected Jam credentials file (`~/.config/jam/credentials.yml`) that supplies the real secrets a Jam brokers/uses, and the demand/supply split between it and the serve config's name-only `credentials:` list.
:read_when: You are supplying the real secrets a Jam brokers or uses — writing ~/.config/jam/credentials.yml, choosing value/command/global/mint per credential, wiring `credentials-file`, or migrating an inline `credentials:`/`bot-token`/`tracker-token` strategy out of a serve config.
:owns: the jam credentials-file format and location, the value/command/global/mint source vocabulary and the minters: library, the `exchange: gcp` demand setting, the demand/supply split (serve config demands by name, the file supplies), which references must name a demanded credential, and fail-closed on an unsupplied demand
:prereqs: serve.adoc for the serve config that demands credentials
:tier: leaf
:updated: 2026-11-13

Jam's real secrets live in one *protected file*, never in the serve config:
the serve config only *demands* credentials by name, and this file *supplies*
them, each from one of four <<sources,sources>> — optionally through a
<<minters,minter>>.

== Location

Set `+credentials-file: <path>+` in the xref:usage/jam/serve.adoc#the-serve-config[serve config].
When omitted it defaults to `+${XDG_CONFIG_HOME:-~/.config}/jam/credentials.yml+`.
Keep it mode `0600` and *never commit it*. A missing file is an empty store, so
every demand then fails closed (below).

== Format

[source,yaml]
----
# ~/.config/jam/credentials.yml   (mode 0600, never committed)
minters:                       # inert library; reached only via a mint: reference
  anthropic-fed:
    anthropic:
      oidc:
        auth0:
          tenant: tenant.us.auth0.com
          client-id: jam-minter
          audience: "https://jam.example.com/anthropic"
          client-secret: { command: ["cat", "/run/secrets/auth0-client-secret"] }
      federation: { org: "<org-id>", rule: fdrl_example, service-account: svac_example }
global:                        # optional inert library; reached only via a global: reference
  gh-token: { command: ["gh", "auth", "token"] }
credentials:                   # name -> source: exactly one of value | command | global | mint
  anthropic-key: { mint: anthropic-fed }
  git-pat:       { global: gh-token }
  jam-db:        { value: "dev-only-password" }
  discord-bot:   { command: ["cat", "/run/secrets/discord"] }
  linear-bot:    { command: ["cat", "/run/secrets/linear"] }
----

Each `+credentials:+` entry sets *exactly one* source, validated on load.
`+minters:+` and `+global:+` are *inert* — reached only through an explicit
`+mint:+`/`+global:+` reference, and an entry supplies nothing until the serve
config demands its name.

[#sources]
== Sources

[%header]
|===
|Source |Form |Resolves to

|`+value:+` |a literal string |that string, verbatim
|`+command:+` |a host *argv array* |stdout of running it on the host, trailing newline trimmed
|`+global: <name>+` |a name |`+global[<name>]+`, which must itself be a `value` or `command` (a chain is an error)
|`+mint: <name>+` |a name |a token minted by `jam mint`, built from `+minters[<name>]+` (<<minters,below>>)
|===

A `+command:+` runs on the Jam host — only supply commands you trust.

`+global:+` and `+minters:+` are *never matched by demand name*: a demand called
`anthropic-key` does not pick up a library entry of the same name — only a
`+credentials:+` entry you wrote reaches one.

[#minters]
== Minters

A `+minters:+` profile is a structured identity for xref:usage/jam-mint.adoc[`jam mint`],
exactly one of:

* `+github:+` — `app-id`, `install-id`, `app-key` (a `+value:+` is a *path* to the
PEM, passed as ``+--app-key-file+``; a `+command:+`/`+global:+` supplies the key
*contents*, passed as `+JAM_MINT_GITHUB_APP_KEY+`).
* `+anthropic:+` — `oidc.auth0` (`tenant`, `client-id`, `audience`,
`client-secret` — a source, passed as `+JAM_MINT_AUTH0_CLIENT_SECRET+`) and
`federation` (`org`, `rule`, `service-account`, optional `workspace`).

Resolving `+{ mint: <profile> }+` runs `jam mint <provider>` with the non-secret
fields as flags and the secret ones resolved on the host and passed as env —
never argv. Jam passes no `+--repo+`, which `jam mint github` requires, so a
`github` profile cannot mint through ``+mint:+``: write the invocation as a
`+command:+` instead (`+["jam", "mint", "github", "--app-id", "…", "--install-id", "…", "--app-key-file", "/path/key.pem", "--repo", "owner/name"]+`).

[#demand-and-supply]
== Demand and supply

The serve config's `+credentials:+` is a *name-only list* (the demand):

[source,yaml]
----
credentials:
  anthropic-key:
  jam-db:
  discord-bot:
----

Every place the serve config refers to a secret must name a *demanded*
credential:

[%header]
|===
|Reference |Where

|`store-postgres.password-cred` |the DB password (xref:usage/jam/serve-store.adoc[])
|a connection's credential (`+cred:+` in `connections/<name>.yml` in the config repo), checked when serve starts the connection — the Discord bot token, the tracker token |xref:usage/jam/serve.adoc[serve.adoc] (`runtime.discord.connection`, ``runtime.requisitioner.connection``; the deprecated `bot-token-cred` / `tracker-token-cred` name one directly)
|a destination's `+cred_name+` |validated by the config plan (xref:usage/jam/destinations.adoc[])
|`pool.cred-name` |the pool's anthropic credential (xref:usage/jam/pool.adoc[pool.adoc])
|`ssh.ca-cred` |the studio-collaboration SSH CA key (xref:usage/jam/serve.adoc[serve.adoc], xref:usage/jam/collaboration.adoc[collaboration])
|`metrics.token-cred` |the `/metrics` scrape token (xref:usage/jam/monitoring.adoc#metrics[monitoring.adoc])
|`config.github.cred`, `config.gitlab.cred`, `config.git.cred` |the followed config repo's token, for exactly its URL (for `config.git`, an SSH private key); any source but gcp-exchange or the pool's (xref:usage/jam/config-git-sources.adoc[config-git-sources])
|`+kits.git[].cred+` |a git token for kit sources, by repo-URL prefix; plain static only. The prefix must be https (or loopback http), end in `/`, and have a dotted host or loopback; refs containing `/` need a portless host (xref:usage/jam/serve.adoc[serve.adoc], xref:usage/jam/kits-git.adoc[kits-git])
|===

A demand may carry one non-secret setting, *``+exchange: gcp+``*:
`+vertex-gcp: { exchange: gcp }+`. The supplied value is then a Google credentials
JSON (`+service_account+`, `+authorized_user+`, `+external_account+` or
`+impersonated_service_account+`). The broker swaps it for short-lived
`cloud-platform` access tokens and caches each one, refreshing it 5 minutes
before it expires. If a refresh fails, the broker re-reads the supply (at most
every 10 seconds), so a re-login or a rotated key needs no restart. A destination naming the credential injects the current token,
and the JSON never leaves the host. `serve` refuses an unknown `exchange`, a JSON
of another type, or the pool's credential. See xref:usage/jam/vertex.adoc[vertex.adoc] for its use.

At `serve` startup Jam loads the file, resolves each demanded name on the host in
memory, and *fails closed*: a demanded name with no entry in the file aborts
`serve` before the broker starts, naming the credential and the file. Resolved
values are never written to disk, put on a command line, or logged — errors name
only credentials.

== Migrating an inline strategy

An inline strategy is a *hard parse error*, not a silent alias (unlike the
xref:usage/jam/renamed-from-harbor.adoc[Harbor renames]): a `+command:+`/`+value:+` under
`+credentials:+`, or an inline `runtime.discord.bot-token` /
`runtime.requisitioner.tracker-token`. The error names the field and points at
this file. To migrate, move each strategy into `credentials.yml` under the same
name, leave only the bare name under `+credentials:+`, and replace the inline
token with a connection whose credential names it (the deprecated
`bot-token-cred` / `tracker-token-cred` bind only an existing such connection:
xref:usage/jam/serve.adoc#the-serve-config[serve.adoc]).
