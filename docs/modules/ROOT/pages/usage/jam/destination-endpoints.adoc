= Destination endpoints
:summary: A destination holds a list of named endpoints (subdomain and/or route, upstream, identity-in/apply, allow_paths, git, header logging) that share its credential, env and note; the flat single-route file is one endpoint named after the destination. Covers both file forms, normalisation, host and path matching, the validation rules and the paths Jam reserves.
:read_when: You are giving one service several addresses in one destination (an `endpoints:` list), a destination write or config plan was refused over an endpoint (a name, a clashing route, a reserved path, a subdomain), or you need to know which endpoint the broker picks for a host and path.
:owns: the endpoint model (`jam.Endpoint`, `Destination.Endpoints`), the flat and list encodings and their normalisation, endpoint validation (names, count, address uniqueness, reserved cove paths, subdomains), and the broker's most-specific-endpoint match by host and path
:prereqs: destinations.adoc for destination files and their fields
:tier: leaf
:updated: 2026-11-13

A destination is a group of *endpoints*.
Each endpoint has its own address and upstream;
the destination's `+cred_name+`, `env`, `note` and operator notes apply to all of them.
A role names whole destinations, so it gets every endpoint
(xref:usage/jam/roster.adoc[]).

== The two file forms

The *flat* form is the one destinations always had
(xref:usage/jam/destinations.adoc[]).
It is one endpoint, named after the destination.

The *list* form gives `endpoints:` instead of the endpoint fields:

[source,yaml]
----
# destinations/github.yml
kind: destination
version: 1
cred_name: gh-pat
endpoints:
  - name: rest
    route: /api/v3/
    upstream: https://api.github.com
    identity_in: bearer
    apply: bearer
  - name: graphql
    route: /api/
    upstream: https://api.github.com
    identity_in: bearer
    apply: bearer
env: {GH_HOST: "{host}"}
----

An endpoint takes `name`, `subdomain`, `route`, `upstream`, `+identity_in+`, `apply`,
`+identity_in_spec+`, `+apply_spec+` (xref:usage/jam/header-specs.adoc[header-specs]),
`+allow_paths+`, `git` (xref:usage/jam/connector.adoc[connector]) and
`+log_headers_in+`/`+log_headers_out+`
(xref:usage/jam/destination-header-logging.adoc[header logging]).
A file may not mix the forms, and unknown fields are refused in both.

A list of one endpoint with no `name` is named after the destination.
A destination whose only endpoint is named after it is written back flat,
byte for byte as before endpoints.
So existing files, stored destinations and backups do not change,
and the config plan sees no change in them.
The store (its JSON documents) and backups use the same two forms.

[#matching]
== Matching

An endpoint's address is a `subdomain`, a `route`, or both.
A subdomain is one label under the destinations domain
(xref:usage/jam/destinations.adoc#destinations-domain[]):
the endpoint is reached at `+<subdomain>.<domain><route>+`.
How a studio reaches and resolves that host, and why a new one needs a restart of the session,
is in xref:usage/jam/destinations.adoc#studio-reach[].

The broker matches by host, then path:

* On the Jam host, the endpoint without a subdomain whose `route` is the longest prefix of the path,
across every destination's endpoints.
* On `+<subdomain>.<domain>+`, only that subdomain's endpoints:
the one whose `route` is the longest prefix of the path,
else the one without a route, which takes every path.
An endpoint without a subdomain is never reached there.

No match (an unknown subdomain, a name deeper than one label, or an unmatched path) is *404*,
and no upstream is contacted.
The route is cut off before the request goes upstream;
without a route the path goes on unchanged.
The credential comes from the endpoint's destination
(its default, or the role's mapping);
the identity-in and apply specs, `+allow_paths+` and header logging come from the endpoint.
Header logs carry `endpoint`, and their rate limit is per destination, endpoint and direction.

[#validation]
== Validation

A destination write (admin UI, config plan) is refused with 400 when:

* it has no endpoints, or more than 10;
* an endpoint of several has no `name`, or two share one;
* an endpoint has neither `subdomain` nor `route`, or no `upstream`;
* a `subdomain` is not one lowercase DNS label (`[a-z0-9-]`, at most 63, not starting or ending with `-`, no `--`);
* an endpoint has a `subdomain` and *this Jam has no destinations domain*
(no `destinations:` block in the serve config);
* a route without a subdomain claims a path Jam serves itself on the cove listener —
the route is a prefix of one (`/` claims all of them),
or lies under one's first segment (`/squawks/x/`);
* two endpoints, in this destination or any other, have the same subdomain and route;
* an endpoint's header specs, `+allow_paths+` or header-logging levels are invalid.

A refusal names every problem at once, an endpoint's prefixed with its name when there are several;
the admin API also returns each at its field
(xref:usage/jam/destination-api.adoc[destination-api]).

The reserved paths are one table, `internal/jam/covepaths.go`.
The cove listener's mux (`cmd/jam/mux.go`) dispatches by it,
so a new Jam endpoint added there is reserved at once.
A route on a subdomain may take any path: a request on a subdomain host never reaches Jam's own paths.

A backup import checks the names, the count, that subdomains are DNS labels, and the per-endpoint specs,
but not routes, upstreams or the destinations domain (serve config, like credentials),
so whatever an older Jam stored still imports
(xref:usage/jam/backup.adoc[backup]).

== Where the first endpoint stands in

Some views still show one endpoint: the admin UI's *New destination* form
(a destination's page edits every endpoint, xref:usage/jam/ui-pages.adoc#destination-pages[ui-pages]),
the connector's `+{url}+` and the `/anthropic/` legacy env default
(the first endpoint's address).
The connector names any other endpoint with `+{host:<endpoint>}+` and `+{url:<endpoint>}+`
(xref:usage/jam/connector.adoc[connector]).
`jam destination list` prints a line per endpoint, as `destination/endpoint` when there are several.
