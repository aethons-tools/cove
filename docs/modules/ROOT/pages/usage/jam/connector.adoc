= The studio connector (destination env)
:summary: The studio connector contract — what a studio sets (env vars, git routing) to use the destinations in its scope; destinations declare it with `env`/`git` in their file in the config repo, and Jam assembles each identity's connector. Includes the `gh` (GitHub API) destinations.
:read_when: You are adding a destination a studio needs client-side setup for (env vars like GH_HOST, or git routing), wondering why a studio has (or lacks) some ANTHROPIC_*/GH_* variable, or wiring `gh` through Jam.
:owns: destination `env`/`git`, the template placeholders (incl. `+{host:<endpoint>}+`/`+{url:<endpoint>}+`), git routing by host, the legacy defaults, connector assembly + conflicts, and the GitHub-API (`gh`) destination recipe
:prereqs: destinations.adoc for destinations; roster.adoc for which destinations a role's scope allows
:tier: leaf
:updated: 2026-11-13

A studio reaches Jam's destinations by setting *client env* (and, for git, a
token-free git config). Each destination declares what it needs; Jam assembles
an identity's *connector* from the destinations its grants allow.

== Declaring it on a destination

In the destination's file in the config repo (xref:usage/jam/destinations.adoc[]):

[source,yaml]
----
# destinations/github-api.yml
kind: destination
version: 1
route: /api/v3/
upstream: https://api.github.com
identity_in: bearer
cred_name: gh-pat
apply: bearer
env: {GH_HOST: "{host}", GH_ENTERPRISE_TOKEN: "{token}"}
----

* `+env: {KEY: TEMPLATE}+`, set once for the whole destination.
Placeholders:
** `+{host:<endpoint>}+` = that endpoint's host: `+<subdomain>.<domain>+`
(the xref:usage/jam/destinations.adoc#destinations-domain[destinations domain]), or the Jam host when it has no subdomain.
** `+{url:<endpoint>}+` = `+https://<that host><route>+`, without a trailing `/`.
** `+{url}+` = `+{url:<first endpoint>}+`, `+{base}+` = `+https://<jam host>+`,
`+{host}+` = the Jam host — kept for one-endpoint destinations.
** `+{token}+` = the studio's identity token.
+
An endpoint placeholder must name an endpoint of the destination. Keys must be env-var names; `+JAM_*+` is
reserved. Validated by the plan.
For example, `gh` takes only a host and adds `/api/v3/` and `/api/graphql` itself, so an
endpoint on subdomain `gh` with no route serves it with `+GH_HOST: "{host:<endpoint>}"+`.
* `+git: true+` (on an xref:usage/jam/destination-endpoints.adoc[endpoint]) routes the studio's git for the endpoint's *upstream host*
through its route (insteadOf + a credential helper that reads the token from
env — no secret in gitconfig): upstream `+https://github.com+` rewrites
`+https://github.com/+`, upstream `+https://gitlab.example.com+` rewrites
`+https://gitlab.example.com/+`. Only the scheme and host count (the broker
forwards to nothing else). An endpoint on a subdomain routes it through
`+https://<subdomain>.<domain><route>+` (route `/` when it has none), and the
credential helper is scoped to that host.
* *The token never sits in a template, the store, or a log.* Clients
substitute it in memory, or render it as `+$JAM_IDENTITY_TOKEN+` in a
sourced snippet.

*Legacy defaults* (a destination with no `env`): the `/anthropic/` route sets
`+ANTHROPIC_BASE_URL={url}+` plus `+ANTHROPIC_API_KEY={token}+` (identity-in
`x-api-key`) or `+ANTHROPIC_AUTH_TOKEN={token}+` (identity-in `bearer` — the
xref:usage/jam/pool.adoc[pool] configuration; other identity-in presets and
xref:usage/jam/header-specs.adoc[custom specs] set no token variable); the `/git/` route implies `+git: true+`. Existing
Jams therefore keep exactly their previous studio env. Giving the `/git/`
destination an `env` drops its implied git routing — add `+git: true+` to keep it.

[#assembly-and-conflicts]
== Assembly and conflicts

An identity's connector is the union over every destination in its grants'
effective scopes (xref:usage/jam/roster.adoc[roster.adoc]). Two destinations setting one
variable to *different* values (after endpoint placeholders resolve), or two different git routes
(from any of their endpoints, on any host — one upstream host has one route), is an error —
fail closed, never a silent pick. So is an endpoint on a subdomain the connector must name on a
Jam without a destinations domain (one imported from a backup).

== Delivery

* *Jam-raised studios* get their connector at raise, and jam-studio-agent re-fetches
it before every agent *episode* (each spawn of the agent process), so edits
reach a running studio at its next episode — not within one: a reply delivered
into a live agent (one holding its session open, e.g. for a background task)
runs under the env that episode started with
(xref:usage/jam/studio-agent.adoc#jam-studio-agent-the-in-cove-client[studio-agent]).
* *Host-side clients* call
`GET /connector` on the broker listener with the identity as a bearer (or
`token`) and receive `+{"env": {…}, "git_route": "/git/"}+` — templates still
unexpanded, `+{url}+` and the endpoint placeholders already resolved: to `+{base}<route>+` / `+{host}+` for an
endpoint on the Jam host, to its literal `+https://<subdomain>.<domain>…+` for one on a subdomain. A git destination on
a host other than github.com adds ``+"git_target": "https://<host>/"+``; its
absence means `+https://github.com/+`, so older clients keep routing GitHub.
A git endpoint on a subdomain adds ``+"git_host": "<subdomain>.<domain>"+``: the
route is on that host, not the Jam's. Both fields are additive — a connector without
them is byte for byte what it was — so older clients keep working for every
destination without a subdomain (one ignoring `+git_host+` would route through the Jam host). Unknown/expired
identity → 401; a conflict → 409. Against a Jam without the endpoint (404),
clients fall back to the legacy Anthropic + git contract. The response also
carries `+model_spec+`, the identity's roles' resolved
xref:usage/jam/model-specs.adoc#what-a-cove-applies[model-spec] (names only; host clients ignore it).

`+jam studio inspect <studio> --section env+` shows the connector a studio was last served (redacted) — see xref:usage/jam/inspect.adoc[inspect].

[#notes-for-sessions]
== Notes for sessions

A destination's optional `note` (≤ 300 bytes; `+note:+` in its file, or
the UI's edit form on a branch) is shown to every session granted it, in the Studio layer of
its xref:usage/jam/session-context.adoc[session context], next to the env keys it sets. Write how
to use the route — e.g. "{empty}``gh`` goes via Jam: pass ``+-R $GH_HOST/<owner>/<repo>+``{empty}".
It is not a secret store: never put a credential in it.

== GitHub API for `gh`

`gh` reaches the GitHub API through the broker by treating Jam as a GitHub
Enterprise host: it calls `+/api/v3/…+` (REST) and `/api/graphql`, sending
`+Authorization: token <x>+` — accepted as a bearer identity. Two destinations
cover it (the longer `/api/v3/` route wins for REST); the env on one of them
points `gh` at Jam:

[source,yaml]
----
# destinations/github-api.yml: as above
# destinations/github-graphql.yml
kind: destination
version: 1
route: /api/
upstream: https://api.github.com
identity_in: bearer
cred_name: gh-pat
apply: bearer
# projects/acme/roles/dev.yml
kind: role
version: 1
scope:
  destinations: [anthropic, git, github-api, github-graphql]
  credentials: {git: gh-pat-acme, github-api: gh-pat-acme, github-graphql: gh-pat-acme}
----

The PAT needs Contents plus the API permissions `gh` uses (pull requests,
issues, metadata). Only the API is brokered this way — clone/push with plain
`git` (the `/git/` destination), not `gh repo clone`.
