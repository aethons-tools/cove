:summary: The comms target space and access-graph — kind-prefixed user:/session:/chat:/channel:/work:/worker: targets (human: and ticket: aliases), each naming a channel of the channel log; Scope.Addressing authz and its exemptions, send(to=…) delivery/reply semantics, and target discovery. :read_when: You want a studio's agent to send to someone other than its own ticket (a named human or a channel), or you're granting/scoping who a studio may address.

A studio's `send` can reach more than its home channel:
a *person* (a `dm`),
another *session*'s home channel,
a group of people and sessions (a `group`),
a *room*,
a unit of work's *log*,
or the unit's current *worker* —
each a channel of the xref:usage/jam/intercom.adoc#enabling-it[channel log] — gated by a *comms
access-graph* that mirrors the broker's `Scope`/`Grant` model.

== The target space

A target is *kind-prefixed*, and names a channel:

[%header]
|===
|Target |Channel

|`+user:<name>+` / `+user:<usr_id>+` |the `dm` between the session and that person — or the session's own channel when that person is already in it
|`+session:<label>+` / `+session:<ses_id>+` |that session's home channel (its own session channel); the sender joins it by posting, so replies come back. A ticket session is reached like any other (no `+ticket:+` addressing needed); a label two live sessions share names neither.
|`+chat:<member>,<member>…+` |the `dm` (one member) or `group` (more) of the session and exactly those members, each a `+user:+` or `+session:+` target
|`+channel:<name>+` |the project's room of that name (post-only: the session doesn't join)
|`+work:<key>+` / `+work:<connection>/<key>+` |that unit of work's log (its own is always allowed; another's is post-only); `+ticket:+` is an alias. A GitHub key is `+owner/repo#<n>+` (`+work:acme/board#7+`, or scoped `+work:<connection>/acme/board#7+`), any case or leading zeros naming one ticket; a malformed one is refused with "github ticket key must be owner/repo#<n>".
|`+worker:<key>+` |the `dm` between the session and the unit's current worker (xref:usage/jam/intercom.adoc#enabling-it[the channel log]). With no current worker (or no log yet), `409` with `+{"error": "no-worker"}+`; nothing is held for a later session. The worker addressing itself is `404`.
|===

A person must be a member of the session's project. The same members are the
same `dm` or `group`, however they're listed, so `+worker:+` and `+chat:session:+` reach one `dm` per pair. `+human:<name>+` — the pre-registry form — is
still accepted and read as `+user:+`. A bare name with no known prefix is
*malformed* and always denied.

Addressing allow-lists (`Scope.Addressing`, below) are *glob-capable*, matched
with ``path.Match``: `+user:*+` (any member), `+channel:eng-*+`
(channels by prefix), `+*+` (everything but sessions: `+session:+` needs its own glob). A person matches a glob by either form —
`+user:<name>+` or `+user:<usr_id>+` — so policy can name someone by id (rename-proof;
what Jam itself writes, e.g. a personal session's grant and migrated policy) or
by name. An id is matched only by that exact id, `+user:*+` or `+*+` — a name
pattern like `+user:a*+` never matches an id — so ids never widen a name glob. Globs match only within
their kind (`+user:+`, `+channel:+`, `+ticket:+`, `+session:+`); write each prefix you mean.
`+work:+` and `+worker:+` have no globs of their own:
they match a role's `+ticket:+` globs,
so `+ticket:ACME-*+` allows `+work:ACME-7+` and `+worker:ACME-7+`.
For a GitHub ticket key, `+*+` also crosses its ``/``: `+ticket:*+` and `+*+` reach every ticket, and `+ticket:x/*+` every ticket of owner ``x``'s repos _or_ every ticket scoped to a connection named `x` (`+ticket:x/<key>+`). A GitHub ticket is matched by its canonical key only, and a glob's GitHub-shaped parts are canonical too (lowercased, `+#<n>+` without leading zeros): `+ticket:Acme/*+` reaches `+acme/board#7+`, while `+ticket:acme/board#??+` does not reach `+acme/board#07+` (that is `+#7+`) — so the spelling never changes the answer, and `+ticket:+` and `+session:+` agree. A malformed key with no `+#+` (`+ticket:acme/board+`) is no GitHub form, so `+*+` does not cross its ``/``: it is denied (403) unless a glob covers it as written (`+ticket:acme/*+`), and only then refused as malformed (404).

== The comms access-graph

A ``Role``'s `Scope` gains `+Addressing []string+` — an allow-list of target globs,
alongside `Destinations`. A ``Grant``'s `Override.Addressing`, when set,
*replaces* the role's addressing (no merge — same semantics as `Override.Destinations`).
Set it in the role's file as `scope.addressing`, a list of globs beside
`scope.destinations` (xref:usage/jam/roster.adoc#roles[roster.adoc]):

[source,yaml]
----
# projects/acme/roles/impl.yml
scope: {addressing: ["user:*", "channel:eng-help"]}
----

*Authorization mirrors the broker's ``Decide``:* resolved live at send time,
*additive across the actor's grants in the session's project*. Everything is
*fail-closed*: an unknown actor, an expired token, a role with no addressing, or
a malformed target all deny. A `+chat:+` needs every member in it allowed; a unit of work
other than the studio's own needs a `+ticket:<glob>+` (e.g. `+ticket:*+`). `+session:<glob>+` matches a label or id.

Some sends never consult the access-graph — only the token's expiry:

* The studio's *home channel* (`to` empty on an older turn protocol, or `+session:+` naming itself).
* Its own unit's log (`+work:<its key>+`).
* For a personal session, the person who started it (`+user:<starter>+`, or that person in a `+chat:+`).
* A *reply*: any target naming an existing conversation the session was delivered a message in.

*Authz is checked before existence.* A target whose form no grant's addressing
allows returns *403* — the send is denied without ever asking whether the target
exists. A target that _is_ authorized in form but isn't in the resolving grant's
project (e.g. `+user:*+` is allowed but no member `bob` exists) returns *404*. This
ordering means a 403 never reveals whether a target would otherwise exist.

== `+send(text, to=…)+` — delivery and reply semantics

A squawk reaches its channel's members (in Jam: their inboxes, waking a waiting
session) and is rendered onto the channel's surfaces by the relays
(xref:usage/jam/intercom.adoc#enabling-it[intercom]):

[%header]
|===
|Channel |Rendered |Replies come back

|work |a comment on its tracker issue |comments on the issue → the work log
|dm, group |each person's Discord inbox (a Discord-chat project); a person with none is `@<handle>`-mentioned on the ticket of a session in it |a Discord reply to the post → the `dm` or `group`; a tracker reply lands in the work log, which the worker is in too
|room |its bound surface (a Linear issue or a Discord channel) |from that surface → the room
|session |each person's Discord inbox, as a `dm` is; never a tracker comment |a Discord reply to the post → the session channel
|===

A person posting in a work log, a room or a non-personal session's channel joins
it and hears what follows; a person sees a project's work logs, rooms and those
session channels while they are a member of it.

== Discovering targets: `GET /squawks/targets` / `+list_targets+`

An agent doesn't need to know its addressing in advance. `GET /squawks/targets`
(brokered, self-derived from the caller's identity — no parameters) returns the
actor's authorized-*and*-resolvable targets:

[source,json]
----
{"targets": [{"target": "work:ACME-7", "kind": "work", "name": "ACME-7"},
             {"target": "user:alice", "kind": "user", "name": "alice"},
             {"target": "worker:ACME-9", "kind": "worker", "name": "ACME-9"}]}
----

What the studio may always message comes first:
its own unit's log (when it has one),
and for a personal session the person who started it.
Then come the people, rooms,
other live sessions (`+session:<label>+`, or `+<ses_id>+` when the label is shared),
units of work (`+work:<key>+`),
and the current workers of those that have one (`+worker:<key>+`)
that its addressing allows. Handles are deliberately omitted — the agent addresses by
`+user:<name>+`, not by handle. The `jam-studio-agent mcp` server exposes this as the `+list_targets+` tool,
alongside ``send``'s now-optional `to` argument; see
xref:usage/jam/intercom.adoc#what-the-tools-do[intercom] for the tool surface. The same list,
taken at raise, appears in the session's xref:usage/jam/session-context.adoc[session context].
