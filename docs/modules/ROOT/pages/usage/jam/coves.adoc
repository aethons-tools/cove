Jam keeps a *runtime registry* of the studios it manages — each a raised
Worker or standing Manager — and drives their lifecycle: raise → record → track
status → tear down, self-healing across Jam restarts. This is the spine the
Requisitioner and standing teammates build on.

____
`studio raise` starts a *real* studio on a xref:usage/jam/studio-managers.adoc[Studio Manager] (see xref:usage/jam/coves-raise.adoc[Raising a real
managed studio]). With `runtime.studio-managers` off,
`jam serve` uses a *placeholder launcher* that records a live registry entry but
starts no studio — useful for exercising the registry/supervisor in dev and tests.
____

[#the-model]
== The model

A managed studio has a durable *identity* (a roster xref:usage/jam/roster.adoc[Actor] — token,
grants) and a runtime *Instance* keyed by that actor's id. The Instance carries
two status fields with different owners:

* *Phase* (Jam owns it): `+raising → live → terminating → gone+`, or, when its
studio dies (the reconciler finds it dead, or its agent exits without `end`),
`+→ recovering → live+` — see <<recovery,Recovery>>; a session raised before
recovery existed, or lost with its manager, goes `+→ lost → terminating+`. A `live` studio
waiting for a reply can also go `+→ idled+` — paused (`docker pause`), with
lease-reaping suspended — and back `+→ live+` on reply, or torn down by the
role's xref:usage/jam/turn-end.adoc#idle-timeout[idle timeout] (never for waiting alone); see xref:usage/jam/wake-on.adoc[wake-on] for
the wake-on/pause mechanics.
* *Activity* (the studio reports it, only while `live`): `running | holding | waiting | blocked | done`. Reporting `done` after `end` (or during a teardown)
ends the session; without it the session <<recovery,recovers>>.
`holding` means the turn ended but background tasks are still running — see
xref:usage/jam/turn-end.adoc#holding[turn-end.adoc].

Each Instance is *leased* to the Jam process supervising it. A lease has a
TTL; the owner renews it, and if it expires another process may take over
(reconnect/failover). On restart, Jam re-adopts live Instances from the store
instead of abandoning them — so in-progress work survives a restart.

[#recovery]
=== Recovery

A session whose studio dies — the reconciler finds it dead (lease expired,
probe dead), or its agent exits without calling `end` (it reports `done`) — is
not ended. It goes *``recovering``*: its studio is torn down and its identity
revoked, but its Instance stays, so the Requisitioner still sees its ticket as
worked and its allocator slot stays held; its channels and ticket are left as
they are, and its xref:usage/jam/standing-state.adoc[state volumes] are kept. A dying studio's
late reports are refused.

The supervisor's reconcile loop re-raises it *under the same id*, on the
manager it ran on while that is still configured, with the prompt it was first
raised with; the new studio finds its conversation marker and
xref:usage/jam/standing-state.adoc[resumes] instead. Its inbox cursor, focus, ticket report,
alarms and escalation category carry over. The first attempt is 30s after the
studio died; a failed attempt backs off (doubling, capped at 30m). Waiting on
infrastructure — the kit's image still building, no manager available — is
retried every 30s and uses up no attempt. After 5 failed attempts, or 2h, or
once its manager is gone, Jam *gives up*: a final teardown, the ticket marked
blocked if unfinished (xref:usage/jam/turn-end.adoc#reporting-a-ticket[turn-end.adoc]), the slot
released. An End (or a standing dismissal or reset) that lands while a re-raise
is in flight wins: the new studio and identity are rolled back. The state sweep
spares a session's volumes while it has an instance or an identity (a raise in
flight).

An operator's *Restart* (xref:usage/jam/session-view.adoc[session-view.adoc]) uses the same
path at once: it is refused for a session being ended or that asked to `end`.

Not recovered (ended as before): a session that asked to `end`, one lost
together with its manager (removed or force-revoked — its state went with it),
and one raised before recovery existed. The rail shows a recovering session as
_recovering_; the admin console lists it under attention.

[#managers-and-placement]
=== Managers and placement

Jam raises studios on named *managers*: remote Studio Managers (see xref:usage/jam/studio-managers.adoc[studio-managers.adoc], enabled by `runtime.studio-managers`).
A raise may name where it may run, and how long to wait for a place:

* `+--manager <name>+` (repeatable; the order is the preference) on `studio raise`
and xref:usage/jam/personal-sessions.adoc#the-verbs[`session request`], or `managers` in the
`POST /admin/coves` and `POST /admin/sessions/personal` bodies. Jam tries the
named managers in that order and raises on the first that is available.
* With none named, Jam tries every manager in registration order.
* `+--placement-timeout <duration>+` (`+placement_timeout+`, a Go duration such as
`30s`) is how long to wait for a manager to become available. `0`, or leaving it
out, means do not wait: the raise fails at once if none is available.
* An unknown manager name is refused; a named manager that is not connected is
skipped, and the raise fails once the timeout runs out.

The manager a studio runs on is shown as `manager=<name>` in `studio list` and as
`manager` in the cove summary.

A xref:usage/jam/standing-sessions.adoc#state-across-restarts[standing session] is *pinned* to
the manager holding its state and is only ever raised there. A
xref:usage/jam/standing-sessions.adoc#reset[reset] clears the pin, so the next raise places it
afresh; so does a pin to a manager that is no longer configured (container names:
xref:usage/jam-colima.adoc#names-and-moving-between-managers[jam-colima]).
Standing raises come from the reconciler, which names no managers today; when a caller does supply
a `managers` list that excludes the pinned manager, the raise is refused with
"standing session is pinned to a manager the request excludes".

[#the-studio-verbs]
== The `studio` verbs

----
jam studio raise    --id spider-42 --role guest [--project acme] [--unit AET-9] [--prompt-file task.md] [--manager NAME ...] [--placement-timeout 30s]
jam studio list     # id  name  role  unit  phase  activity  lease-holder  connector  image  manager=
jam studio status   --id spider-42 --activity waiting
jam studio teardown --id spider-42
----

* `studio raise` starts a *new session* (a minted `+ses_…+` id, printed) and
enrolls its identity (the role must exist — fail-closed), recording a `live`
Instance. It takes an ephemeral slot under the role's cap first, like a
Requisitioner raise (`409` when the cap is reached). `+--id+` is the session's *label*: unique among live sessions (409
otherwise), it addresses the session in `status`/`teardown` (as does its id),
and is free again once the session ends — a later raise under it is a new
session that inherits nothing. The role supplies scope, exactly as with
xref:usage/jam/roster.adoc[enroll]. `+--prompt-file+` supplies the workload prompt (read
host-side, never on argv) — required by the real launcher; see xref:usage/jam/coves-raise.adoc[coves-raise].
* `studio status` reports the studio's activity; `+--activity done+` triggers teardown.
* `studio teardown` tears the studio down and revokes its identity (idempotent).
* `connector` (in `studio list` and the admin UI Agents list) is `ok` when the studio's latest agent episode (agent process) started with its role's current connector, `stale` when a destination or grant changed since (it refreshes at the next episode — a wake delivered into a live episode does not refresh it), `unknown` when it never reported (an image built before the per-spawn refresh — re-raise it), `error` when Jam cannot compute the current connector to compare against (the studio's actor is no longer on the roster, or its role's destinations conflict). Because the git route is part of the fingerprint, a studio whose git-config rewrite failed reports the route actually in effect, so it shows `stale` until the rewrite lands on a later episode.
* `image` (in `studio list`, xref:usage/jam/standing-sessions.adoc#declaring-one[`standing list`], the admin UI Agents list and the role page's standing rows) is `ok` when the studio runs the image a raise for its role would run now, and `stale` when that image has changed since the raise. The comparison is against the current tag on the studio's own manager (a legacy record with no manager means `local`). The image changes when the role's kit changes a build-affecting field, its xref:usage/jam/model-specs.adoc[model-spec] harness changes (CLI version, plugins), the manager's build inputs change (a new jam-colima binary, Jam host or the manager's identity key — its assembly fingerprint), or the role stops raising a kit at all. Each Instance records the tag it was raised on (`+image_tag+`) and its kit ref (`kit`); the current tag is resolved by the same code a raise uses, cached per kit version and harness. Without both tags (a studio raised before tags were recorded, or a launcher that cannot name images) Jam compares the recorded kit: a different kit or build digest is `stale`, the same one `unknown`. It is also `unknown` when the role's current kit or model-spec does not resolve; the listing never fails on it, and the reason is logged at debug level (once per role per minute). Terminating, lost and gone studios show `-`. A stale studio keeps its old image until it is torn down and raised again; a standing one is moved to the current image with xref:usage/jam/standing-sessions.adoc#upgrading-a-standing-session[`standing upgrade`]. `GET /admin/coves?project=&role=` lists one role's studios. `jam role images <project>/<role>` (admin `+GET /admin/roles/{project}/{role}/images+` → `+{"images":[{manager,kit,has_kit,tag}]}+`) shows the role's current image on every connected manager, one `+<manager>\t<kit>\t<tag|->+` line each; 404 for a missing role, 422 for an unresolvable setup, 503 without a supervisor.

Raising a real studio on a Studio Manager — the raise sequence, kit-prepare and egress drift: xref:usage/jam/coves-raise.adoc[coves-raise].

Managed studios are also raised *automatically* by the xref:usage/jam/requisitioner.adoc[resident
Requisitioner] — an always-on loop that polls a tracker and raises one
per ready ticket — not only by this manual `studio raise` verb.

A raised studio's agent also gets a brokered xref:usage/jam/intercom.adoc[intercom MCP] — `read`/`send`
on its own ticket — so it can converse (ask, leave a status) on the ticket it's working.
A studio is not one-shot: after each turn it *waits* (Activity `waiting`) and Jam
*wakes* it to resume (`+claude --continue+`) when a reply lands, an alarm fires, or its
idle timeout passes — see xref:usage/jam/turn-end.adoc[turn-end.adoc].

All `studio` verbs take the admin-client flags (`+--app+`/`+--admin-url+`/`+--token+`);
see xref:usage/jam/operators.adoc[operators.adoc].

== Tuning the supervisor (`+runtime:+`)

Optional serve-config block (see xref:usage/jam/serve.adoc[serve.adoc] for the whole config):

[source,yaml]
----
runtime:
  lease-ttl: 60s            # how long a lease is valid without renewal
  reconcile-interval: 30s   # reconcile + renew cadence (must be < lease-ttl)
----

Defaults are `60s` / `30s`. `reconcile-interval` must be strictly less than
`lease-ttl` so a live owner always renews before its own lease expires.

Design rationale (the identity/runtime split, the lease/steal model, the
reconciler) lives in
https://github.com/aethons-tools/cove/blob/main/docs/superpowers/specs/2026-09-12-harbor-cove-supervisor.md[`../../superpowers/specs/2026-09-12-harbor-cove-supervisor.md`].

Each managed studio holds one stream to Jam, and `jam-studio-agent` in the studio runs its agent: xref:usage/jam/studio-agent.adoc[studio-agent].
