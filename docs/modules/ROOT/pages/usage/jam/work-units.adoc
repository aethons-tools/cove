= Units of work: the record, its API, and its page
:summary: The record Jam keeps for each unit of work—its issue, the sessions that have been its worker, the pull requests reported for it, and its last reported state—how worker swaps, reports, and the PR watcher write it, its tables (`work_units`, `work_unit_workers`, `work_unit_prs`) and backfill, `GET /app/user/api/work/\{key}`, and the unit's page in the Jam app (`/app/user/w/<key>`).
:read_when: You are reading or changing what Jam records about a unit of work (`jam.WorkUnitStore`, `Intercom.Reported`, the worker swap in `ownTicketChannel`), its tables or migrations, the PR watcher that posts reviews, merges, and closes to the work log (`prWatcher`, `runtime.requisitioner.pull-requests`), the work API (`userui.apiWork`), the unit's page (`web/app/src/work/`), or the rail's `WorkRow.state`.
:owns: the unit of work's record (`jam.WorkUnit`), when it's written, the PR watcher, its storage, `GET /app/user/api/work/\{key}`, and the unit's page in the Jam app (`/app/user/w/<key>`). Does NOT own the work log and its current worker (intercom.adoc), the `report` tool (turn-end.adoc), the rail (rail-api.adoc), or who may open a session view (session-view.adoc).
:prereqs: intercom.adoc for the work log and its worker; turn-end.adoc for `report`
:tier: leaf

A unit of work is one tracker issue as Jam sees it
(the Jam manual's *Units of work*).
Its log is a `work` channel, and the channel holds only its current worker
(xref:usage/jam/intercom.adoc[intercom]).
The *record* keeps the rest, keyed by the log's channel id (`jam.WorkUnit`):

* *The issue:* its title and URL, as the Requisitioner raised a worker with them
(`Instance.UnitTitle`, `Instance.UnitURL`: the `url` of a Linear issue, the `html_url` of a GitHub one).
* *Workers:* every session that has been the unit's worker,
in the order they started, with its label, when it started, and when it stopped.
* *Pull requests:* every PR reported for the unit,
in the order first reported: URL, number, title, state (`open`, `merged`, or `closed`), and when it was first reported.
* *State:* the unit's state as last reported
(`in-progress`, `in-review`, `needs-input`, `blocked`, or `done`), and when.

The API below, the rail's `WorkRow.state`, and the <<pr-watcher,PR watcher>> read it.

[#writes]
== Writes

* *A worker swap.*
When a session becomes the unit's worker (`Intercom.ownTicketChannel`, at raise and at serve start),
Jam MUST record a new worker starting now, stopping the previous worker at the same time.
Recording the current worker again MUST be a no-op,
so a restart doesn't add a turn.
The session's issue title and URL, when set, replace the unit's.
* *A session ends* (`Intercom.Ended`):
its turn MUST stop now when it's the current worker.
* *A report* (`Supervisor.SetReport`, from `report` or from wake-on's `blocked` for a session that ended without one):
Jam MUST record the state, and the `pr` URL as a new `open` PR when the unit has no PR with that URL.
The number is parsed from the URL's `/pull/<n>` (or `/merge_requests/<n>`); `0` when it has none.

* *The PR watcher* (<<pr-watcher,below>>):
it MUST record a PR's title and its state.

Every write is best effort: a failure is logged and MUST NOT fail the swap, the end, or the report.
A record exists from its first write; every write needs the channel to be a `work` log.

[#pr-watcher]
== The PR watcher

The PR watcher (`cmd/jam/relay_prs.go`) is the GitHub relay's pull request side.
It posts a unit's pull request reviews, merge, and close to the unit's work log.
It runs with the Requisitioner and polls at the Requisitioner's `poll-interval` (a minute when unset).

* *What it reads.*
Each poll, it MUST read every `open` PR of every live work log
whose URL is a github.com pull request:
the pull request, then its reviews (`githubissues.Client.PullRequest`, `PullReviews`).
A `merged` or `closed` PR MUST NOT be read again.
A PR on another host, or one the token can't read, is skipped with one warning per serve.
* *What it posts.*
For each submitted review (approved, changes requested, commented, or dismissed; never pending),
then for a merge or a close,
it MUST post one entry to the work log:
the outcome, and a markdown link to the review or the pull request,
for example `approved pull request [#744: Title](…#pullrequestreview-1)`.
The entry's author is the GitHub account that reviewed, merged, or closed it,
recorded as the tracker relay records a comment's author (`directory.author`):
the member linked to that account, else the account
(GitHub's `ghost` when GitHub names nobody).
* *Like any entry.*
The entry has no origin,
so the tracker relay MUST mirror it onto the issue (as `pass:c[<account>: ]`, a person's prefix),
and it wakes the unit's worker as a person's post does (xref:usage/jam/wake-on.adoc[wake-on]).
* *Once.*
The entry's id names the event:
`pr:<owner/repo>#<n>:review:<review id>`, `pr:<owner/repo>#<n>:merged`, or `pr:<owner/repo>#<n>:closed`.
The channel log refuses an id it already holds (`intercom.ErrDuplicateID`),
and the watcher MUST treat that as posted,
so a re-poll or a restart MUST NOT post an event twice,
even when a restart comes between the post and recording the PR's state.
The watcher MUST offer every submitted review of an open PR,
not only those past a mark:
GitHub gives a review its id when it's started,
so a review left pending can be submitted after a later one.
It remembers the ids it posted while it runs,
so only the first poll after a restart offers the log a review again.
* *Its token.*
`runtime.requisitioner.pull-requests` names a `github` connection to read with
(xref:usage/jam/requisitioner.adoc[requisitioner]);
unset, a GitHub Issues tracker reads with its own connection,
and a Linear tracker has no PR watcher.
A rate limit ends the poll, and the watcher makes no calls until GitHub's `Retry-After` has passed.
Each open PR costs two calls a poll (three when it's closed) on that token's hourly budget,
which a GitHub Issues tracker shares with its own polls.

[#storage]
== Storage

Migration `0028_work_units.sql` adds three tables, each removed with its log's channel:

[%header,cols="1,3"]
|===
|Table |Holds

|`work_units`
|One row per unit: `channel_id`, the issue's `title` and `url`, `state` (`''` = none), `state_at`.

|`work_unit_workers`
|One row per worker's turn, ordered by `ord`: `session_id`, `label`, `started_at`, `stopped`, `stopped_at`.
A `NULL` time isn't known.

|`work_unit_prs`
|One row per PR, ordered by `ord`, unique by `url`: `number`, `title`, `state`, `reported_at`.
|===

A write rewrites the unit's rows in one transaction (`putWorkUnitTx`).

The migration backfills workers from each `work` log's session members (`channel_members`):
a past member (`left_seq` set) as a stopped worker,
the log's current worker as the current one.
A member's start is its instance's `raised_at` while the instance still exists, otherwise unknown;
its stop time is unknown.
A session called into a log isn't told apart from a worker.

[#api]
== API

`+GET /app/user/api/work/{key}+` (`userui.WorkUnit`) returns the live unit with issue key `+{key}+`
(a Linear key, or a GitHub `owner/repo#<n>` with `#` escaped)
in the caller's projects.

* Access MUST follow the work log's:
someone who may read the log (a project member, or a member of the log) may read the unit.
Anyone else, and a key with no live log, MUST get `404` with `code: "not_found"`, the same answer.
* A log with no record yet MUST return the unit with empty `workers` and `pullRequests`.

[%header,cols="1,3"]
|===
|Field |Holds

|`key`, `title`, `url`
|The issue key, title, and page.
`title` falls back to the current worker's `UnitTitle`; empty when not known.

|`log`
|The work log's channel id.

|`state`
|The last reported state; empty when none.

|`workers`
|Each turn: `session`, `label`, `started` and `stopped` (absent when not known, or `stopped` while current), `current`,
and `view`: the session view's path (`/app/user/s/<session>`) when the caller may open it
(xref:usage/jam/session-view.adoc[session-view]), else empty.

|`pullRequests`
|Each PR: `url`, `number`, `title`, `state`, `reportedAt`.
|===

The <<page,unit's page>> reads it.
The rail's `WorkRow` carries the same `state`
(xref:usage/jam/rail-api.adoc#sections[rail-api]).

[#page]
== The page

`/app/user/w/<key>` (`web/app/src/work/`) shows a unit of work
from <<api,its API>>, in the xref:usage/jam/intercom-ui.adoc[Jam app].
A Work row in the rail and a ticket session's ticket in the session header open it.

* *Header:* the key and title, each linking to the issue's `url`;
the state as a chip (`in-progress`, `in-review`, `needs-input`, `blocked`, `done`; none when empty);
the tracker's name (*Linear*, *GitHub*, else the URL's host) linking to the issue;
and the work log's *Needs you*, *Call in*, *Join*, and *Leave*, as a conversation header's.
* *The log:* the work log as the conversation view shows it (`ConversationView` with a `frame`):
its messages, open asks, status strip, and a composer posting to the log; it marks the log read.
* *The panel* (`WorkPanel`), folded to a strip by *Hide* and back by its *⟨* (in the page only, not remembered):
*Agents* lists the current worker first, then the past ones, newest first,
each with when it worked as far as the record knows;
the current worker's status is the rail's `WorkRow.worker.state` (a `UnitWorker` has none),
shown when the rail's worker is that session.
A worker links to its `view` when set, otherwise its label is plain text.
*Pull requests* lists each with its `#<n>` (the URL when `0`) linking to it, its title, and its state as a chip.
* *Narrow screens* (`(max-width: 900px)`, the session pane's breakpoint):
the log and the panel are two tabs, *Log* and *Agents & pull requests*.
* *Not found:* a `404` from the API (no such unit, or one the viewer may not read) MUST show the app's "Nothing here." page.
The page refreshes with the `work` query on every `changed` signal and the 30 s poll.
