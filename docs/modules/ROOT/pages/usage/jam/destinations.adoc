= Destinations
:summary: A destination — one brokered upstream, a file `destinations/<name>.yml` in the config repo: its route, upstream, identity and credential presets, env/git, `allow_paths`, header logging, note and default credential — and the destinations domain that reaches endpoints by subdomain.
:read_when: You are adding or changing a destination a studio reaches through Jam, choosing its `identity_in`/`apply`, `allow_paths` or `cred_name`, setting up the `destinations:` domain so a client reaches an endpoint by subdomain, or a brokered request got 403/400/404 from the route or path rules.
:owns: the destination file and its fields, `jam destination list`, the no-repo-policy rule, and the destinations domain (DNS, certificate, SNI, host routing, how studios reach subdomain endpoints)
:prereqs: serve.adoc for the broker model and the serve config; credentials.adoc for the credentials a `cred_name` names; destination-endpoints.adoc for several endpoints in one destination
:tier: leaf
:updated: 2026-11-13

A *destination* is one brokered upstream: a path prefix on the broker that maps
to an upstream base URL plus how the identity arrives and how the real credential
is applied. A destination is a file in the config repo,
`destinations/<name>.yml` (xref:usage/jam/config-git.adoc#layout[config-git]); add, change or
remove one by a commit:

[source,yaml]
----
# destinations/anthropic.yml
kind: destination
version: 1
route: /anthropic/
upstream: https://api.anthropic.com
identity_in: x-api-key
cred_name: anthropic-key
apply: x-api-key
----

[source,yaml]
----
# destinations/git.yml
kind: destination
version: 1
route: /git/
upstream: https://github.com
identity_in: basic-password
cred_name: git-pat
apply: basic-password
----

`jam destination list` prints them.
A destination can also hold several named endpoints (an `endpoints:` list), which share
its credential, env and note; the fields below then go on each endpoint, except
`+cred_name+`, `env` and `note` — see xref:usage/jam/destination-endpoints.adoc[destination-endpoints],
which also gives the routes Jam refuses.

* `+identity_in+` / `apply` are a preset, `bearer | basic-password | x-api-key | raw` —
how the studio presents its identity, and how Jam applies the real credential;
other headers take a custom spec (`+identity_in_spec+` / `+apply_spec+`) — see xref:usage/jam/header-specs.adoc[header-specs].
The identity header is always stripped before forwarding, so a Jam identity
token never reaches the upstream.
* `+oauth_beta+` was *removed* (a file carrying it is refused): the broker now adds that beta for every
xref:usage/jam/pool.adoc#the-oauth-beta[pool] credential.
* `+env: {KEY: TEMPLATE}+` and `+git: true+` declare what a studio must set
to use the destination — see xref:usage/jam/connector.adoc[connector], which also covers
the `gh` (GitHub API) destinations.
* `+allow_paths: [PATTERN, …]+` limits what the broker forwards: a
https://pkg.go.dev/path#Match[`path.Match`] pattern over the path _after_ the
route (`+*+` never crosses ``/``; a path with `..` or `//` never matches). Any other
path is refused *403* before the credential is resolved. No patterns means
any path. Use it when the injected credential reaches more than the cove
needs. xref:usage/jam/vertex.adoc[] uses it to limit a GCP token to Claude model calls.
* The broker forwards the path after the route *as the client escaped it*,
so an encoded segment such as a GitLab project id `group%2Frepo` reaches the
upstream intact. `+allow_paths+` matches its decoded form; a request whose
route prefix arrives percent-encoded is refused *400*.
* `+log_headers_in: none|examined|all+` / `+log_headers_out: none|changed|all+`
turn on redacted troubleshooting header logs for the destination — see
xref:usage/jam/destination-header-logging.adoc[destination-header-logging].
* `note` (≤ 300 bytes) is a usage hint shown to sessions granted the destination —
see xref:usage/jam/connector.adoc#notes-for-sessions[connector].
* `+cred_name+` must resolve to a `+credentials:+` entry in the serve config —
or, when the xref:usage/jam/pool.adoc[pool] is enabled, the pool's `cred-name` (which the
pool resolves by identity, not from `+credentials:+`). Validated by the plan.
It is the destination's *default* credential: a role may map the
destination to a different one (xref:usage/jam/roster.adoc[]).
* *No repo policy.* Jam does not scope a git destination by ``owner/repo``; the
injected credential's own scope is the boundary. Use a fine-grained PAT per
project (one `+credentials:+` entry each) and map it per role.
*Upgrading from a repo-scoped Jam widens access:* a role that relied on
`+--repos+` to narrow a broad PAT gets that PAT's full reach — re-scope the
credentials before upgrading. Stored `+repo_scoped+`/`repos` keys are ignored.

These admin verbs take the standard client flags (`+--app+`/`+--admin-url+`/`+--token+`);
see xref:usage/jam/operators.adoc[].

[#destinations-domain]
== The destinations domain

With a `destinations:` block, an endpoint can be reached by *subdomain*
(xref:usage/jam/destination-endpoints.adoc#matching[destination-endpoints]),
so a client that only takes a host, such as `gh`, needs no path of its own:

[source,yaml]
----
destinations:
  domain: jam.example.com          # may be the Jam host itself
  tls: { cert: /etc/jam/dest.crt, key: /etc/jam/dest.key }
----

* *DNS and certificate are the operator's,* as for previews: point `+*.<domain>+`
at the broker listener, and supply a wildcard certificate for `+*.<domain>+`.
serve fails at startup if the certificate does not cover it.
* *SNI picks the certificate.* The broker listener presents the wildcard certificate
to a client naming a host under the domain, and the `tls` certificate to every other
client (no SNI, the domain itself, any other name).
* *Host routes before path.* A request whose `Host` is under the domain goes straight
to the broker, ahead of the Attach gRPC and Jam's own cove paths (`/connector`,
`/squawks`, `/metrics`, …), which are never reached there. The broker serves the
subdomain's endpoints; an unknown subdomain, a name deeper than one label, or an
unmatched path is *404* without contacting an upstream. Every other host is served
as before.
* serve refuses a `listen` host under the domain (its requests would all go to the
broker). The domain itself may be the Jam host.
* [[studio-reach]]*Studios reach subdomain endpoints* when their Studio Manager sets
`colima.destinations-domain` to the same domain
(xref:usage/jam-colima.adoc#destinations-domain[jam-colima]).
The manager then bakes `+.<domain>+` into the studio's infra egress list,
so the role's egress does not have to name it.
`/etc/hosts` cannot hold a wildcard, so each raise maps named hosts instead.
Jam sends the hosts (`+<subdomain>.<domain>+`) of the subdomain endpoints of the destinations
that the role grants. The manager maps each one to the host gateway, as it maps the Jam host.
Hosts of other destinations are not mapped.
* *A new subdomain endpoint needs a restart of the session.* The raise fixes the hosts of a studio.
If you add an endpoint, or grant a role a destination, after the raise, restart the session
(xref:usage/jam/session-view.adoc[session-view]) so that its studio resolves the new host.
* The agent connector names subdomain endpoints' hosts
(`+{host:<endpoint>}+`, `+{url:<endpoint>}+`) and routes git through them
(xref:usage/jam/connector.adoc[connector]).
