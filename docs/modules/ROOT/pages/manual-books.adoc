= Books and search on the team site
:summary: The team site's books (Antora components on "Jam books" — the Jam manual, the architecture book from docs/, and the process book from the private aethons-tools/jam-config, pulled in by manual/extensions/books.js from a local clone or CI checkout with the JAM_CONFIG_DEPLOY_KEY secret) its full-text search (@antora/lunr-extension) with the UI contract it needs, and its UI (spring-io/antora-ui-spring, pinned and sha256-verified, plus our supplemental files).
:read_when: You are adding a book to the team site, building the team site with or without the process book, setting up its jam-config deploy key, touching search or the book switcher, or changing or bumping the team site's UI bundle.
:owns: the team site's books (the content sources and manual/extensions/books.js), the architecture book's and the process book's branch-to-version mappings and how it is pulled in (JAM_CONFIG_DIR, JAM_CONFIG_DEPLOY_KEY), search (@antora/lunr-extension and the UI's side of it), the team site's UI (antora-ui-spring, scripts/manual-ui.sh, manual/ui-spring), and diagrams in the books (manual/extensions/diagrams.js)
:prereqs: manual.adoc for the manual, its versions and its builds
:tier: leaf
:updated: 2026-11-13

* *Books.* The team site, titled _Jam books_ (``site.title``; the customer
manual stays _Jam manual_), hosts several books, each an Antora component:
this manual is `jam`. The "…" button beside the book's name in the nav opens
the book and version panel: every component (`site.components`) and each of
its versions. To add a book, add a content source to
`antora-playbook.yml` (and `antora-playbook.local.yml` if it should build
locally): a repo `url`, `+start_path+` to the dir holding its `antora.yml`
(its own `name`, `title`, `nav`), and `branches` — or, for a repo not
everyone can read, an entry in the `books` list (below), which also suits a book some
branches don't have yet. Its pages use our UI and
extensions; `internal` applies to it as to `jam`. Never add one to
``antora-playbook.jam.yml``: the customer manual is `jam` alone
(`scripts/manual.sh` and the extension tests check it).
* *The process book* (`process`, _Process_: how we run Jam's development)
lives in the private `aethons-tools/jam-config` under ``process/``; its
`main` is version `current` (the default) and `goal` is `goal`. A missing
branch, or one without `process/`, is skipped. Antora's git can't do SSH and
a playbook can't read the environment, so it is not a content source: the
`books` list of `manual/extensions/books.js` in `antora-playbook.yml` adds it
from a local clone — `+$JAM_CONFIG_DIR+` (which must then exist), else
`../jam-config` beside your cove checkout, else none (a warning, and the site
is the manual alone). It reads the local branch of each name, else origin's,
like cove's; fetch first. CI checks jam-config out into the workspace with
the read-only deploy key in secret `+JAM_CONFIG_DEPLOY_KEY+` (not kept for later
steps) and sets ``+JAM_CONFIG_DIR+``; without the secret it warns and deploys the
manual alone. Tests: `manual/extensions/test/books.test.js`.
* *The architecture book* (`architecture`, _Architecture_: how cove is
built) is this repo's `docs/` (`docs/antora.yml`; its layout is in
xref:docs-asciidoc.adoc[]). Its versions are the manual's: `release` is
`released`, `main` is `next`, `goal` is `goal`. On the team site it is an
entry in the `books` list (`dir: ..`, cove itself), not a content source,
because a branch without `docs/antora.yml` would fail the build (`release`
until the book is released; `goal` until `main` is merged in): `books.js`
skips such a branch with a warning. The local playbook adds it as a content
source from your working tree, like the manual. Never in the customer
manual: `scripts/manual.sh` fails if an `architecture/` directory ends up in
it, and the extension tests check the customer playbook.
* *Search* is `@antora/lunr-extension` (pinned in `manual/package.json`),
enabled in the team and local playbooks only: the customer manual is
embedded in Jam, whose CSP allows no scripts, and `scripts/manual.sh` fails
if a search index ends up in it. It writes `search-index.js` at the site
root (all books and versions, internal content included — the site is
Access-gated; about 50 KB today). The UI's side of the contract, in
`ui-spring/partials/header-content.hbs` and `search.hbs`, all under ``+{{#if env.SITE_SEARCH_PROVIDER}}+``:
`<input id="search-input" type="text">` inside `+#search-field+` (the results
dropdown attaches to it), an "In this book" checkbox
(`+data-facet-filter="component:<name>"+`), and
`+{{> search-scripts}}+` before `</body>` (the extension supplies that partial,
`lunr.js`, `search-ui.js` and ``search.css``; the UI must not ship them). The
indexer reads only `article.doc` and takes the title from its `h1.page`, so
keep page content in them.
* *Diagrams* are code, in every book.
A `+[mermaid]+` listing block in a page
(`+[mermaid,alt="…"]+` then `+----+`-delimited Mermaid source)
is rendered at build time into an SVG file
by `manual/extensions/diagrams.js`,
an Antora extension that every playbook registers,
the customer one included.
The block becomes an image of that file,
added to the page's module as a generated image (never committed),
so the page shows it as an `<img>`:
Mermaid styles its SVG with an inline `<style>`,
which Jam's CSP for the customer manual (`default-src 'self'`, no `style-src`) blocks in an inline SVG
but not in an image file.
The extension runs `@mermaid-js/mermaid-cli` (`mmdc`, pinned in `manual/package.json`,
`PUPPETEER_SKIP_DOWNLOAD` so it fetches no browser)
with the headless Chrome `just manual-shot` uses
(`+$JAM_BROWSER+`, else the kit's `/opt/chrome-headless-shell`).
Every build that renders the books needs that Chrome:
`manual-site.yml`, and `scripts/manual.sh`, so also `just build`
and the release (goreleaser runs `scripts/manual.sh`), which set `+JAM_BROWSER+` to the runner's Chrome.
The SVG carries no script.
`alt` is required and becomes the image's alt text and the SVG's `<title>`.
Diagrams follow the internal rules like any image:
a diagram in internal content is dropped from the customer manual
(xref:manual.adoc[], "Marking content internal");
every other diagram is in it.
Rendered SVGs are cached under `manual/build/diagrams/` by a hash of the source and the `mmdc` version,
so a rebuild renders only what changed.
A block that fails to render, or has no `alt`, fails the build with the page and line.
No other diagram tool, no client-side rendering,
and no committed images of diagrams:
the source in the page is the only copy.
Screenshots stay images (xref:manual.adoc#screenshots[]).
* *The team site's UI* (team and local playbooks) is
https://github.com/spring-io/antora-ui-spring[spring-io/antora-ui-spring]
v0.4.26 (MPL-2.0); the customer manual keeps `manual/ui` (no scripts: Jam's
CSP), and must never use it. Antora's own `ui.bundle.url` fetch can't check
a checksum, so `scripts/manual-ui.sh` (run by `just manual`, `just
manual-site` and `manual-site.yml`) downloads the release's `ui-bundle.zip`
to `manual/build/ui-spring.zip` (git-ignored), checks its pinned sha256
(it fails, keeping nothing, on a mismatch) and the playbooks read that path;
`runtime.fetch` stays false. *To bump it*, set `version` and `sha256` in
the script (the checksum of the new release asset, `+sha256sum+` of a copy you
have looked at), rebuild, and check our partials against the new theme's
(below). TODO: a Renovate custom regex manager on the script's `version`.
* *Our additions*, `manual/ui-spring/` (`ui.supplemental_files`), replace
theme partials by name: `header-content` (site title, search box and "In
this book" filter, the theme's dark-mode toggle), `main` and `article`
(breadcrumbs and the Next/Goal banners outside `article.doc`, so search
doesn't index them; no "newer version" notice), `toc` (no edit or GitHub
links), `nav-tree` (the "Team only" badge), `search` (lunr's scripts, not
Algolia), `head-scripts` (our `css/jam.css`, not analytics),
`related-projects` (empty) and `footer-content` (the licence notice).
Licence: MPL-2.0 is per file. The bundle's own files ship unmodified, notices
kept; our overrides are separate files, not edits to the bundle. Those adapted
from a theme partial (`header-content`, `main`, `article`, `toc`, `nav-tree`;
each says so) are MPL-2.0 like the original; the rest (`css/jam.css`
included) are ours. Never edit the zip itself.
